# Архитектура аварийного доступа

## Назначение

ESP32-S3 работает как независимый аварийный бастион для восстановления доступа
к основному Linux-ПК, если основной WireGuard-туннель на ПК перестал работать.

Целевой сценарий:

```text
Удалённый ноутбук/телефон
          │
          │ WireGuard через один из двух VPN-серверов
          ▼
      ESP32-S3
          │
          │ локальная сеть 192.168.1.0/24
          ▼
Linux-ПК 192.168.1.200:22
          │
          └── диагностика и перезапуск основного WireGuard-туннеля
```

ESP32 не должна предоставлять произвольный доступ ко всей локальной сети. Она
разрешает только заранее определённые аварийные действия и TCP-туннель к
`192.168.1.200:22`.

## Проверенное окружение

| Параметр | Значение |
|---|---|
| Основной ПК | Linux |
| IP основного ПК | `192.168.1.200/24` |
| Аварийный сервис | SSH, TCP `22` |
| Подключение ПК | Wi-Fi, интерфейс `wlan0` |
| Wi-Fi-адаптер ПК | a Wi-Fi adapter, драйвер `the driver` |
| Wake-on-Wireless | Настроен и активен: Magic Packet, GTK rekey |
| Профиль NetworkManager | `MyHomeWiFi` |
| PCI wakeup | `enabled` |
| MAC для пробуждения | `AA:BB:CC:DD:EE:FF` |
| Broadcast локальной сети | `192.168.1.255` |
| Основной VPN | WireGuard |
| VPN-серверы | Два, active/passive failover |

IP ESP32 назначается по DHCP. Постоянный адрес закрепляется на роутере.

## SSH-бастион и терминальный интерфейс

ESP32 поднимает SSH-сервер только после установления WireGuard-туннеля. В
production разрешена только аутентификация по публичным SSH-ключам; парольная
аутентификация отключена.

Сразу после входа пользователь видит сводный экран:

```text
ESP32 Recovery Gateway
────────────────────────────────────────
Device uptime       12d 04:18:31
Wi-Fi               ONLINE  -42 dBm
Internet            ONLINE
WireGuard            ONLINE  server-1
Last handshake       8s ago
VPN server-1         ACTIVE  31 ms
VPN server-2         STANDBY 47 ms
Main PC              ONLINE  192.168.1.200
SSH :22              OPEN
Free heap / PSRAM    ... / ...
Last reset           watchdog / power-on / software
────────────────────────────────────────
Type 'help' for commands.
```

Планируемые команды:

| Команда | Назначение |
|---|---|
| `status` | Однократная сводка состояния |
| `watch` | Обновляемый терминальный dashboard |
| `pc ping` | Проверка доступности `192.168.1.200` |
| `pc ssh` | Открыть TCP-туннель к `192.168.1.200:22` |
| `pc wake` | Отправить Magic Packet основному ПК |
| `vpn status` | Активный профиль, endpoint, handshake и ошибки |
| `vpn failover` | Вручную перейти на следующий VPN-профиль |
| `vpn retry-primary` | Принудительно проверить основной профиль |
| `logs` | Последние диагностические события из кольцевого журнала |
| `reboot` | Перезагрузить ESP32 после подтверждения |
| `help` | Показать разрешённые команды |

`help` является частью интерфейса, а не только документации. Полная структура,
подробная справка и конкретные примеры команд описаны в
[cli-reference.md](cli-reference.md). Реализация должна строить справку из того
же реестра команд, который вызывает обработчики, чтобы текст не расходился с
фактическими возможностями прошивки.

Для обычного SSH к Linux-ПК предпочтителен стандартный SSH `direct-tcpip`
channel. Он позволяет использовать ESP32 как jump host, не создавая общий
SOCKS-прокси и не включая маршрутизацию всей подсети.

## Wake-on-Wireless LAN

ESP32 может самостоятельно отправить Magic Packet в локальную сеть; отдельный
сервер для отправки не требуется. Однако пробуждение с Wi-Fi зависит от
адаптера, драйвера, BIOS/UEFI и режима питания Linux-ПК.

На текущем ПК WoWLAN настроен и активен в профиле `MyHomeWiFi`. Адаптер
a Wi-Fi adapter с драйвером `the driver` поддерживает Magic Packet, PCI wakeup
включён. ESP32 должна отправлять пакет на `192.168.1.255` для MAC
`AA:BB:CC:DD:EE:FF`.

Эталонная ручная проверка из другого устройства этой локальной сети:

```bash
wakeonlan -i 192.168.1.255 AA:BB:CC:DD:EE:FF
```

Перед проверкой основной ПК переводится в сон:

```bash
systemctl suspend
```

Фактический тест ещё не выполнен, чтобы не прерывать рабочий сеанс.
Поддерживаемый целевой режим — пробуждение из `s2idle`; после полного выключения
WoWLAN обычно не работает.

В журнале драйвера присутствует предупреждение UBSAN, связанное с `the driver`.
Сейчас оно не мешает Wi-Fi, но должно проверяться первым, если Magic Packet не
разбудит компьютер или соединение после resume не восстановится.

Если конкретный Wi-Fi-адаптер или BIOS не поддерживает нужный режим питания,
резервным вариантом будет подключение ESP32 через опторазвязку/реле параллельно
к кнопке питания ПК.

## Два WireGuard-профиля

ESP32 хранит два независимых профиля:

- `server-1` — основной;
- `server-2` — резервный.

Алгоритм active/passive:

1. После загрузки ESP32 пытается установить туннель через `server-1`.
2. Одна потерянная проверка не вызывает переключения.
3. После нескольких последовательных неудач и устаревшего handshake профиль
   считается недоступным.
4. ESP32 закрывает текущий интерфейс и активирует `server-2`.
5. Пока `server-2` работает, устройство остаётся на нём и не возвращается на
   основной сервер самопроизвольно.
6. При отказе `server-2` цикл начинается снова: сначала проверяется `server-1`,
   затем `server-2`.
7. Команда `vpn retry-primary` позволяет проверить основной сервер вручную.

Переключение должно использовать hysteresis, несколько проб и backoff, чтобы
потеря одного пакета не вызывала постоянное переключение между серверами.

Одновременно активен только один WireGuard-профиль. Для профилей допускаются
разные endpoint, tunnel IP, private key, peer public key и preshared key.

## Импорт WireGuard-конфигурации

Визард принимает стандартный файл WireGuard `.conf` отдельно для основного и
резервного профиля. Поддерживаемые поля:

```ini
[Interface]
PrivateKey = ...
Address = ...
DNS = ...

[Peer]
PublicKey = ...
PresharedKey = ...
Endpoint = host:port
AllowedIPs = ...
PersistentKeepalive = ...
```

Перед сохранением конфигурация должна быть разобрана, проверена и показана без
секретных значений. Невалидный файл не заменяет последний рабочий профиль.
Обновление обоих профилей выполняется транзакционно с возможностью rollback.

### Безопасность визарда

Передавать WireGuard private key через открытую Wi-Fi-сеть `ESP32_SetUp`
небезопасно: находящийся рядом злоумышленник может перехватить или подменить
конфигурацию.

Поэтому разделяем provisioning на два этапа:

1. Открытый `ESP32_SetUp` используется только для подключения ESP32 к Wi-Fi.
2. WireGuard-профили и SSH public keys импортируются через USB либо через
   защищённую сессию после физического подтверждения кнопкой `BOOT`.

Для серийного устройства предпочтительна уникальная provisioning identity и QR
на корпусе, позволяющий аутентифицировать устройство до передачи секретов.
Private keys никогда не записываются в Git, логи или диагностический dashboard.

## Надёжность

- независимые задачи Wi-Fi, internet health, WireGuard, SSH и watchdog;
- контролируемый failover между двумя VPN-профилями;
- `PersistentKeepalive` для работы за NAT;
- восстановление после обрыва Wi-Fi и смены внешнего IP;
- аппаратный watchdog и учёт причины каждой перезагрузки;
- кольцевой журнал без секретных данных;
- A/B OTA, проверка новой версии и автоматический rollback;
- последняя рабочая конфигурация сохраняется до проверки новой;
- brownout detection и стабильное независимое питание;
- в production: Secure Boot V2, Flash Encryption и подписанные обновления.

## Этапы реализации

1. SSH-сервер в локальной сети, public-key authentication и dashboard.
2. Проверки `192.168.1.200:22`, команда `pc ssh` и кольцевой журнал.
3. Испытание уже настроенного WoWLAN из `s2idle`, затем команда `pc wake`.
4. Один WireGuard-профиль и удалённый SSH-доступ только к ESP32.
5. TCP bastion до `192.168.1.200:22` через WireGuard.
6. Второй профиль, автоматический failover и ручные команды управления.
7. Безопасный импорт конфигурации и rollback.
8. A/B OTA, watchdog fault injection и длительное soak-тестирование.
9. Production hardening: Secure Boot, Flash Encryption, уникальные ключи.

## Открытые решения

- способ безопасной первичной передачи WireGuard private keys;
- точные тайм-ауты и число неудач до failover;
- формат хранения SSH authorized keys;
- доступность ESP32 SSH только через WireGuard или также из LAN;
- новая LED-индикация для состояния VPN без конфликта с текущими цветами Wi-Fi;
- способ аппаратного включения ПК, если WoWLAN не работает после полного
  выключения;
- результат фактического теста WoWLAN и влияние предупреждения UBSAN `the driver`.
